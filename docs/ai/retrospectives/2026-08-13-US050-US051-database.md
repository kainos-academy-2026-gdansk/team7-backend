## What was delivered

Added the database foundation for US050 and US051 without changing application code. The Prisma schema now contains an `Application` model linked to `User`, `JobRole`, and the existing `Status` table. It stores required `experience` (`VARCHAR(1000)`), `salaryExpectation` (`VARCHAR(100)`), and `skills` (`VARCHAR(2000)`), includes timestamps, prevents duplicate applications per applicant and role, and indexes applications by role and status. Migration `20260813113654_add_application_model` also adds `IN_PROGRESS`, `HIRED`, and `REJECTED` rows to the shared status lookup table. Follow-up migration `20260813121456_cascade_delete_applications_with_job_role` makes role deletion cascade to linked applications. CV/S3 storage, API layers, confirmation, notifications, and assessment behavior remain deferred.

## What went well

- The implementation stayed within the requested database-only scope: one Prisma schema edit and one migration.
- The migration was generated in create-only mode, inspected, then amended with idempotent shared-status inserts before application.
- Fresh Testcontainers verified the migration chain, while the existing development database was updated without resetting data.
- The unique applicant/job-role constraint and compound role/status index were included before API implementation, giving later services a stable persistence contract.
- Deferring CV/S3 fields avoided committing to a storage representation while the requirement is technically blocked.

## What went wrong

- The initial proposal considered a new application enum before the requirement was corrected to reuse the existing Status table. **Root cause:** the user story and existing schema use different status domains, and the first proposal optimized for domain separation before the shared-table constraint was confirmed.
- The shared Status foreign key cannot enforce that JobRoles use only `OPEN`/`CLOSED` and Applications use only `IN_PROGRESS`/`HIRED`/`REJECTED`. **Root cause:** a single integer FK has no entity-specific category constraint; later services must validate status names by domain.
- The first review identified restrictive role deletion as an unresolved risk. **Resolution:** the follow-up migration changes only `Application.jobRoleId` to `ON DELETE CASCADE`; confirmation and optional notifications remain outside the database layer.
- The first live metadata command omitted Prisma's required `--schema` argument. **Root cause:** the command syntax differs for `prisma db execute` in this repository; the corrected command completed successfully.

## Rework and declines

The model was revised during planning: the proposed enum was removed, the existing Status table became the Application status FK, and the experience, salary expectation, and skills fields were added as required bounded strings. CV/S3 fields were explicitly deferred. No implementation decline occurred after the revised proposal.

## Time and effort signals

There was one discovery round, two clarification rounds for status and field decisions, one schema validation pass, one create-only migration inspection, one corrected verification command, and one full validation run. No tests or application code needed rework.

## Candidate lessons

| # | Lesson | Destination | Developer decision |
| - | ------ | ----------- | ------------------ |
| 1 | When one lookup table serves multiple domain entities, document the valid status subset for each entity and enforce that subset in the owning service because the shared FK cannot enforce it. | `decisions.md` | Accepted |
| 2 | Generate schema migrations in create-only mode when they contain lookup-row inserts, inspect the SQL, and use status names rather than environment-dependent numeric IDs for later defaults. | `testing.md` | Accepted |
| 3 | Keep provisional free-form database fields bounded and record the migration trigger for later structured requirements, especially for salary data. | `memory.md` | Accepted |
